## Current implementation and decisions

Normal tasks use detached worktrees, fixed writable/protected policy, full regression verification, a new-pass acceptance ratchet, optional strict review, resumable state and compare-and-swap publication. v0.2 added Codex roles, sequential mixed-provider delegation and usage accounting. v0.3 added opt-in isolated parallel workers, atomic call reservations, sibling cancellation, plan-order Git three-way integration and bounded text resolvers. Unsupported structural conflicts reject. Existing task fingerprints remain compatible.

The current request adds an Evo²-inspired, opt-in **fixed-weight harness evolution** workflow. Its Proposer and Reflector share one frozen evolver specification. Autonomous edits are paired with fresh parent evaluation; reflection chooses keep, revise or adaptation of an evaluated donor strategy. A bounded pool retains root and champion with depth/recent representatives. Nodes retain parent/donor provenance and raw role/evaluation evidence, including weak or regressing executable candidates.

A candidate replaces the champion only with positive paired mean change, observed mechanism activation, no task regression against its fresh parent and scores dominating the champion. Every directed edit is reevaluated; reflection credit derives from that intervention, not feedback prose. Result publication uses a separate local branch and lease. No default self-modification, weight training, automatic remote push or scientific promotion occurs. Evolution resume is deliberately unsupported; a new id means a new explicit budget.

## Evidence and changed judgment

Before implementation: Evo²'s fixed-weight Proposer–Reflector design was a plausible reusable mechanism, but it could also add unproductive critique overhead or optimize development-only artifacts. The decisive engineering checks were whether matching, scope, activation and regression gates reject misleading improvements while allowing real fixture changes.

Observed: 108 local tests passed (24.523 seconds), including 22 evolution tests with actual subprocesses/worktrees. Coverage includes directed/crossover provenance, paired repeated task/executor/seed requests, absent activation, regressions, frozen evaluators, invalid/mutating roles, missing results, startup failure, budgets, timeout, interruption, reused ids and branch movement. The installed 0.4 wheel runs its offline evolution demo outside source. Codex preparation makes no inference calls. Evidence: tests/test_evolution.py, proofloop/evolution.py, proofloop/evolution_demo.py, docs/validation.md.

Earlier controller evidence: 30 tests at v0.1, 57 at v0.2, 86 at v0.3; no-key code/data/report/parallel examples complete. v0.3 passed six hosted Linux/macOS Python 3.11–3.13 jobs. v0.4 CI must be checked after publication. These are cumulative fixture families, not independent evidence of model quality.

Interpretation: supported within the fixture scope is the control-flow and rejection behavior. The alternative explanation—extra search overfits development cases without useful transfer—remains unresolved. No live Astra/Sol/Qwen inference, cost reduction, accuracy gain, hard sandbox, Windows validation, weight training or replication of paper benchmark results is claimed. Evaluator identity echoes do not prove actual provider settings; the trusted evaluator must enforce them.
